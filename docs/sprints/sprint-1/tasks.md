S1-16 is a documentation deliverable only; product tests are implemented in later sprints. The testing matrix must have separate groups for Client Integration (`client/tests/integration/`), Server Integration (`server/tests/integration/`), E2E (`tests/e2e/`), and Regression (`tests/regression/`). ## Status and Review Conventions

- Keep status values consistent: `Not started`, `In progress`, `Blocked`, or `Done`.
- A task is `Done` only when its acceptance criteria have been reviewed and evidence is linked or identified in the task discussion/PR.
- If a task is blocked by access, credentials, or a team decision, record the blocker and next action; do not place secrets in this document.
- The task-board deadline column is authoritative if other Sprint 1 planning notes differ.

## Architecture and Testing Standards

These standards apply to every implementation task in this plan. Planning, documentation-only, and provider-configuration tasks do not require product tests unless they change code or test/CI wiring.

- Keep client/server code feature-first under `client/src/features/<feature>/` and `server/src/features/<feature>/`; reserve each app's `src/shared/` for cross-feature primitives.
- Separate auth journeys into `client/src/features/auth/login/` and `client/src/features/auth/registration/`. Keep chat, tickets, knowledge, RAG, dashboards, and actions in their own feature boundaries as they are introduced.
- A feature owns its UI or route handler, service logic, API/data access, validation/types, and feature-specific tests. Expose intentional public interfaces; do not couple features by importing one another's internal files.
- Put genuinely reusable UI, API clients, errors, configuration, and logging in `src/shared/`; do not use `shared` as a dumping ground for feature-specific behavior.
- Keep client and server tests in their respective `tests/integration/` folders; keep root-level tests limited to `tests/e2e/` and `tests/regression/`. Put reusable test data and setup in `tests/helpers/` or `tests/mocks/` rather than accumulating unrelated fixtures in a single test file. Use fictional data and test-only credentials.
- Organize application code feature-first under `src/features/<feature>/`. In the server, keep routes, controllers, services, and feature types within the feature boundary; use `src/config/` for cross-feature runtime configuration such as CORS. Create a feature `types/` directory when it owns multiple type definitions.
- The original S1-02 source-code deferral and root `.env.example` requirement were planning assumptions; the repository foundation follow-up superseded them. The implementation and final environment layout are recorded below.
