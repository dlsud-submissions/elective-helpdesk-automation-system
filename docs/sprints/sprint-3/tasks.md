## Architecture and Testing Standards

These standards apply to every implementation task in this plan. Planning/documentation-only work is exempt from product tests unless it changes code or test/CI wiring.

- Keep frontend journeys in `client/src/features/<feature>/`: separate auth login and registration at `auth/login/` and `auth/registration/`, and keep chat, tickets, and dashboard capabilities in their own features. Keep only truly reusable UI and API primitives in `client/src/shared/`.
- Keep backend auth, chat, tickets, actions, and analytics in `server/src/features/<feature>/`; reserve `server/src/shared/` for reusable infrastructure. Features expose intentional public interfaces instead of importing another feature's private components, state, or persistence code.
- Separate presentation, domain rules, transport/API access, and persistence/integration adapters; put validation and feature types with the feature that owns them.
- Every code task that changes behavior adds or updates unit tests for isolated feature logic, integration tests for UI/API/auth/database/webhook boundaries, and E2E regression tests for the supported user path it changes. E2E cases use fictional users/data and include success plus relevant failure/denial paths.
- Keep unit tests alongside their feature or in `__tests__/`; use `client/tests/integration/` and `server/tests/integration/` for boundary tests, and `tests/e2e/` for complete browser journeys. Do not substitute mocked component tests for API integration or E2E coverage.
- S3-07 runs the full unit, integration, and E2E regression suite for login, cited chat, ticket creation, escalation, agent follow-up, and authorization denial.
