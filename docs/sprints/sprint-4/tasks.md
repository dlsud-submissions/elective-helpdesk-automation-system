## Architecture and Testing Standards

These standards apply to every implementation task in this plan. Documentation/report-only tasks are exempt from product tests unless they change code or test/CI wiring.

- Keep fixes inside the owning capability under `client/src/features/<feature>/` or `server/src/features/<feature>/`; put only genuinely cross-feature components/adapters in `client/src/shared/` or `server/src/shared/`.
- Preserve clear boundaries among UI, domain/business rules, API transport, persistence, and external integrations. Auth login/registration remain distinct client feature areas; ticket, chat, knowledge/RAG, action, and dashboard features must not import one another's private internals.
- Every behavior-changing fix adds or updates unit tests for the faulty logic, integration tests for the affected API/database/auth/provider boundary, and an E2E regression test for the user journey that exposed the issue. Existing critical flows remain in the full regression suite.
- Keep unit tests by feature; store cross-module checks in `client/tests/integration/` or `server/tests/integration/`; keep complete regression journeys in `tests/e2e/`. Security, privacy, RAG quality, resilience, and accessibility cases must have repeatable evidence.
- S4-07 runs all unit, integration, and E2E suites after fixes; a defect is not closed until its regression test fails before the fix or otherwise demonstrates the corrected behavior.
