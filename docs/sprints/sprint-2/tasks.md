## Architecture and Testing Standards

These standards apply to every implementation task in this plan. Planning/documentation-only work is exempt from product tests unless it changes code or test/CI wiring.

- Put backend capabilities in `server/src/features/<feature>/` and reserve `server/src/shared/` for truly cross-feature infrastructure. Use feature-owned modules for `tickets`, `knowledge`, `rag`, and `chat`; keep route, domain, persistence adapter, validation, and types cohesive within each feature.
- Client work, if needed for API verification, belongs in `client/src/features/<feature>/`; cross-feature UI/API primitives belong in `client/src/shared/`.
- Do not make one feature import another feature's internal files. Define deliberate public interfaces and keep provider/database details behind the owning feature or shared adapter boundary.
- Every code task that changes behavior adds or updates unit tests for business logic/chunking, integration tests for API/database/Gemini-adapter boundaries (with Gemini mocked or stubbed and no live secrets), and E2E regression tests for the complete API-to-data-to-answer behavior available in this backend-focused sprint. When a UI exists, E2E tests must exercise it as well.
- Keep unit tests beside the feature or in its `__tests__/` area; use `server/tests/integration/` for service/API/data boundaries and `tests/e2e/` for end-to-end regression flows. Use deterministic fictional seed data and no live secrets.
- S2-07 verifies all three layers locally and in CI, including clean migration/seed setup, ticket operations, grounded answers, citations, and safe no-result behavior.
